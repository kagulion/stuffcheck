Когда вы подключаете к проекту AI-ассистента — будь то Claude, Cursor, Copilot Workspace или автономный агент DeepMind / Antigravity — он начинает работу с чистого листа. У него нет контекста вашей команды, он не знает негласных договоренностей и с радостью начнет переписывать архитектуру, изобретать велосипеды или использовать библиотеки, от которых вы отказались три года назад.

Решение этой проблемы — файл `AGENTS.md` в корне вашего репозитория.

> **Главное отличие**: `README.md` пишется для людей (быстрый старт, установка, общие цели). `AGENTS.md` — это жесткая операционная система и онбординг-гайд для **AI-агента**, определяющий границы дозволенного, архитектурный стек и протокол проверки кода.

---

## 1. Фундаментальный принцип: Архитектор и Исполнитель

Самая частая ошибка разработчиков — надеяться, что AI-агент сам примет правильные архитектурные решения.

* **Вы** — архитектор продукта и источник истины.
* **AI-агент** — исполнительный инженер, который строго реализует поставленную задачу в заданных рамках.

Если дать агенту слишком размытую задачу, он будет действовать по пути наименьшего сопротивления модели:

```md
<!-- ❌ Плохой запрос (слишком свободный) -->
Сделай страницу поиска с AI-фильтрацией и красивым UI.

<!-- ✅ Хороший системный запрос -->
Реализуй полноэкранную страницу поиска по документам. 
- Бэкенд: серверный роут /api/search с валидацией через Zod.
- UI: используй готовые карточки из components/SearchCard.astro.
- Перед написанием кода: предложи план реализации и дождись подтверждения.
```

## 2. README.md против AGENTS.md

Зачем плодить отдельные файлы, если уже есть `README.md` и `CONTRIBUTING.md`?

| Критерий | `README.md` | `AGENTS.md` |
| :--- | :--- | :--- |
| **Целевая аудитория** | Разработчики-люди, пользователи | AI-агенты, LLM-ассистенты |
| **Стиль изложения** | Описательный, дружелюбный | Императивный, строгий, структурированный |
| **Фокус внимания** | Установка зависимостей, демо | Антипаттерны, границы прав, протокол проверок |
| **Уровень детализации** | Верхнеуровневый обзор | Специфичные команды CLI, схемы данных, лимиты |

## 3. Анатомия идеального AGENTS.md

Хороший `AGENTS.md` не должен быть бесконечной «простыней» текста (иначе он переполнит контекстное окно модели). Он состоит из **6 ключевых блоков**:

### Блок 1. Роль и рабочий процесс (Workflow Protocol)
Задайте алгоритм, которому агент обязан следовать **до** того, как вставит первую строчку кода:

1. **Изучить контекст**: прочитать связанные файлы и типы данных.
2. **Уточнить неясности**: задать *один* конкретный вопрос, если требования противоречивы.
3. **Составить план**: описать список планируемых изменений.
4. **Реализовать задачу**: писать код только в рамках плана.
5. **Провести самопроверку**: запустить линтер, тайпчек и тесты.
6. **Сдать отчет**: предоставить краткое резюме с результатами тестирования.

### Блок 2. Технологический стек и «Черный список»
Четко укажите не только то, что *нужно* использовать, но и то, что **категорически запрещено**:

```md
### Разрешенный стек
- Фреймворк: Next.js 15 (App Router)
- Стилизация: Tailwind CSS v3 (только утилитарные классы)
- Валидация: Zod v3
- Иконки: Lucide React

### Черный список (Запрещено)
- ❌ Не устанавливать сторонние UI-библиотеки (MUI, Chakra, AntD).
- ❌ Не использовать CSS Modules или inline-стили.
- ❌ Не создавать микросервисы или отдельные Node.js серверы — все API строго в App Router.
- ❌ Не использовать `any` в TypeScript.
```

### Блок 3. Безопасность и границы ответственности
Агенты склонны случайно отправлять приватные токены на клиент или вызывать LLM напрямую из браузера. Зафиксируйте правила безопасности:

```md
### Границы архитектуры
- **Клиент (Browser)**: только отображение UI и вызовы безопасных API-роутов.
- **Сервер (Next.js API / Server Actions)**: работа с базой данных, валидация, вызовы LLM и MCP.

### Секреты и токены
- 🟢 Публичные (безопасно для клиента): `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`
- 🔴 Приватные (СТРОГО на сервере): `OPENAI_API_KEY`, `DATABASE_URL`, `CLERK_SECRET_KEY`
```

### Блок 4. Правила работы с UI и дизайном
Если у вас есть дизайн-система или макеты, зафиксируйте статус источника истины:

* **Pixel-perfect по эталону**: если предоставлен скриншот или Figma-макет — повторить отступы, типографику и состояния hover/active 1-в-1.
* **Переиспользование компонентов**: перед созданием новой кнопки или карточки агент обязан проверить директорию `src/components/`.
* **Mobile-first**: адаптивность делается аккуратно, без поломки десктопной сетки.

### Блок 5. Протокол валидации (Definition of Done)
Агент не имеет права считать задачу выполненной, пока не выполнит обязательный набор консольных команд:

```bash
# Обязательный чек-лист перед отчетом:
npm run lint          # Проверка ESLint без предупреждений
npm run type-check    # Проверка типов TypeScript (tsc --noEmit)
npm run build         # Успешная тестовая сборка проекта
npm run test          # Запуск unit-тестов
```

### Блок 6. Формат финального отчета
Чтобы вам не приходилось читать километры логов, потребуйте от агента строгую структуру финального ответа:

* **Что сделано**: краткий список изменений (3–5 пунктов).
* **Как протестировано**: результаты выполнения сборки и тестов.
* **Внимание разработчика**: неявные допущения, оставленные TODO или вопросы.

## 4. Готовый шаблон AGENTS.md (Starter Kit)

Вы можете скопировать этот шаблон в корень своего репозитория и адаптировать под свой стек:

```markdown
# AGENTS.md — Инструкция для AI-ассистента

## 1. Роль и принципы
Ты — старший инженер-разработчик. Ты пишешь чистый, поддерживаемый код, строго следуя архитектуре проекта.
Перед началом работы изучи код, типы и существующие компоненты.

## 2. Рабочий процесс
1. Сформулируй краткий план действий.
2. Реализуй изменения минимально необходимым объемом кода.
3. Запусти обязательные проверки: \`npm run type-check\` и \`npm run lint\`.
4. Сформируй итоговый отчет.

## 3. Стек и ограничения
- **Стек**: TypeScript, Tailwind CSS, Astro / Next.js.
- **Архитектура**: строгое разделение клиента и сервера. Никаких приватных ключей на клиенте.
- **Стилизация**: используй цвета и классы существующей дизайн-системы. Не добавляй кастомные цвета без необходимости.

## 4. Критерии готовности (DoD)
- [ ] TypeScript компилируется без ошибок (\`tsc --noEmit\`).
- [ ] Линтер проходит без ошибок (\`eslint .\`).
- [ ] Сборка \`npm run build\` завершается со статусом 0.
- [ ] Сохранены все существующие комментарии и логика, не относящаяся к задаче.

## 5. Формат отчета
- **Что изменено**: список файлов и их назначение.
- **Проверки**: статус сборки и тестов.
- **Замечания**: важные нюансы для ревьюера.
```

- [x] Опишите стек и 3–5 главных антипаттернов (чего агенту делать нельзя).
- [x] Добавьте команды для проверки типов и линтинга.
- [x] Зафиксируйте правила безопасности для токенов и ключей API.

`AGENTS.md` — это живой документ. Дополняйте его каждый раз, когда ловите ассистента на повторяющейся ошибке. Через 2–3 итерации ваш AI-напарник начнет выдавать код уровня senior-разработчика вашей команды с первой попытки.
