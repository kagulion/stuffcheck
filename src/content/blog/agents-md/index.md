# Введение

> `AGENTS.md` — один из самых важных файлов в проекте, использующем AI-ассистентов.

Он предназначен не для пользователей. Он не является аналогом вашего `README`. Он написан для ИИ-агента, который будет помогать в разработке приложения.

Цель этого файла проста. Когда ИИ приступает к работе, он уже должен понимать продукт, стек, правила, рабочий процесс и границы проекта.

Для этой обучающей платформы `AGENTS.md` объясняет, что представляет собой приложение, как должен работать ИИ, как следует реализовывать пользовательский интерфейс, как моделируется контент, как работает поиск, как обрабатываются видео, что должно оставаться конфиденциальным и какие проверки необходимо выполнять.

Вот почему этот файл важен. Он предоставляет ИИ систему для следования, вместо того чтобы оставлять каждое решение открытым во время реализации.

## Начните с правильного мышления

Прежде чем писать `AGENTS.md`, четко поймите разделение ролей. Вы — мыслитель продукта. ИИ — исполнительный агент.

**ВЫ:** Вы — мыслитель продукта.

**ИИ:** ИИ — исполнительный агент.

ИИ может работать быстро, но он не должен отвечать за определение того, что представляет собой продукт, какой должна быть архитектура или какие компромиссы важны. Это мышление принадлежит вам.

Ваша задача — определить продукт, стек, границы, правила и рабочий процесс. Задача ИИ — выполнять работу внутри этой системы.

Пример слабого начального запроса:

- _Создай мне обучающую платформу с AI-поиском._

Это дает ИИ слишком много свободы. Он может выбрать неправильную модель данных, создать неправильный поисковый опыт, раскрыть приватные значения, создать нежелательные маршруты или добавить функции, выходящие за рамки текущей разработки.

Более сильная начальная точка выглядит так:

_Вы создаете обучающую платформу, где авторы создают курсы в Sanity, а учащиеся просматривают их, смотрят уроки и ищут информацию по всему контенту курсов. Поиск должен основываться на данных Sanity, возвращать структурированные карточки результатов и ссылаться на точные временные метки в видеоуроках. Перед реализацией напишите файл с промптом, запросите утверждение, а затем строго придерживайтесь утвержденного плана._

В этом и заключается разница. Вы не просите ИИ спроектировать всю систему в процессе реализации. Вы сначала даете ему систему.

`AGENTS.md` — это место, где живет эта система.

# Прежде чем писать файл

Не открывайте пустой файл `AGENTS.md` и не начинайте добавлять случайные правила. Сначала проясните продукт.

Для обучающей платформы начните с основных вопросов о продукте. Что делает приложение? Кто создает контент? Кто потребляет контент? Где находится контент? Какие страницы использует учащийся? Какие части являются общедоступными? Какие части требуют аутентификации?

Затем углубитесь. Что делает этот продукт уникальным? Что должен возвращать поиск? Что поиск никогда не должен выдумывать? Какие данные должны оставаться приватными? Что еще не должно быть построено?

Для этого проекта продукт ясен. Авторы создают контент курсов в Sanity, а учащиеся используют приложение Next.js для просмотра курсов, открытия уроков, просмотра видео и поиска по учебному контенту.

Выдающейся функцией является интеллектуальный поиск. Учащийся должен иметь возможность ввести запрос на естественном языке и получить полезные карточки результатов, которые указывают на реальные курсы, реальные уроки или точные моменты внутри видеоуроков.

Это одно продуктовое решение влияет почти на все остальное. Это влияет на схему Sanity, конвейер обработки видео, API поиска, карточки результатов, поведение временных меток, а также на обязанности сервера и клиента.

Поэтому, прежде чем писать `AGENTS.md`, проясните продукт. Затем напишите инструкции.

# Относитесь к AGENTS.md как к руководству по эксплуатации проекта

Хороший `AGENTS.md` — это не просто список предпочтений. Это дисциплинированное руководство для того, как ИИ должен работать внутри кодовой базы.

Для этой обучающей платформы файл должен отвечать на важные вопросы. Что мы строим? Как должен работать ИИ? Как должна обрабатываться работа над пользовательским интерфейсом? Какие навыки должен читать ИИ? Какой стек мы используем? Какие данные мы моделируем? Как работает поиск? Каких ошибок следует избегать ИИ? Какие проверки необходимо выполнять?

Это обеспечивает согласованность ИИ на протяжении всей разработки. Если он забудет, должен ли поиск быть чат-ботом или карточками результатов, `AGENTS.md` ответит на это. Если он попытается раскрыть приватное значение в браузере, `AGENTS.md` скажет "нет". Если он попытается создать собственный видеоплеер, `AGENTS.md` скажет "нет".

Смысл не в том, чтобы сделать файл длинным без причины. Смысл в том, чтобы исключить решения, которые ИИ не должен принимать во время реализации функций.

# Раздел 1: Определите роль ИИ

Начните с указания ИИ, кто он есть. Не пишите что-то расплывчатое, например:

_Ты — полезный помощник по кодингу._

Это не говорит агенту, насколько серьезно относиться к архитектуре, безопасности, поведению продукта или тестированию.

Для этой обучающей платформы ИИ должен действовать как старший партнер по реализации.

_Ты — ведущий полнофункциональный инженер и ИИ-агент по внедрению, создающий производственную обучающую платформу с интеллектуальным поиском контента._

Это задает ИИ правильную позицию. Он не должен вести себя как случайный генератор кода. Он должен думать о структуре, безопасности, качестве реализации, потоке данных и о том, соответствует ли результат реальному продукту.

Затем определите основную задачу.

_Твоя задача — понять запрос, использовать правильные навыки проекта, написать четкий промпт для реализации, получить утверждение, а затем реализовать._

Это одно предложение важно, потому что оно говорит ИИ, что написание кода — не первый шаг. Планирование — это первый шаг.

# Раздел 2: Объясните, что вы строите

В этом разделе следует описать продукт простым языком. ИИ должен понимать приложение как продукт, а не просто как набор технологий.

Для обучающей платформы вы можете объяснить это так:

_Это обучающая платформа. Авторы создают курсы в Sanity, а приложение Next.js обслуживает эти курсы для учащихся. Учащиеся могут просматривать курсы, открывать страницы курсов, смотреть уроки и искать информацию по учебному контенту._

Затем объясните, что делает приложение особенным.

_Выдающейся функцией является интеллектуальный поиск. Учащийся вводит запрос на простом языке и получает ранжированные кликабельные карточки результатов. Эти карточки могут вести на курсы, уроки или точные секунды в видеоуроках, где рассматривается данная тема._

Это важно, потому что ИИ должен понимать цель продукта, стоящую за списком функций. Если он понимает, что поиск является выдающейся функцией, он будет принимать более правильные решения при работе над схемами, транскриптами, маршрутами поиска, карточками результатов и воспроизведением по временным меткам.

После этого перечислите, что входит в область действия, простым языком. Для этого проекта это включает в себя: модель контента Sanity, аутентификацию, страницу каталога, страницу деталей курса, страницу урока, страницы инструкторов, прогресс учащихся, аналитику PostHog, обработку транскриптов, конфигурацию поиска и сам поисковый интерфейс.

Затем четко добавьте границы области действия.

_Не стройте ничего за пределами этого. Не перестраивайте._

Это коротко, но важно. ИИ-агенты часто добавляют дополнительные функции, потому что они кажутся полезными. Ваш файл должен четко дать понять, что "полезно" — недостаточно. Функция должна быть в рамках области действия.

# Раздел 3: Опишите рабочий процесс ИИ

Это один из самых важных разделов во всем файле. ИИ не должен открывать кодовую базу и сразу же начинать редактирование.

Для этого проекта рабочий процесс должен быть очень четким.

1.  Прочитай `AGENTS.md`.
2.  Прочитай указанные навыки и любые вспомогательные навыки.
3.  Изучи существующий код и конфигурацию.
4.  Задай только один уточняющий вопрос, если задача действительно неоднозначна.
5.  Напиши промпт для реализации в папке `prompts`.
6.  Запроси утверждение.
7.  Начинай разработку только после утверждения.
8.  Выполни проверки.
9.  Заверши кратким отчетом.

Этот рабочий процесс замедляет ИИ правильным образом. Это предотвращает переход агента к реализации до того, как он поймет запрос, существующий код или границы задачи.

Промпт для реализации должен включать: цель, прочитанные навыки, изученный код, решения и допущения, ожидаемые файлы, требования, соображения безопасности, критерии приемки, проверки для запуска и шаги ручного тестирования.

Этот файл промпта становится планом. Вы проверяете план, прежде чем ИИ коснется кода.

Рабочий процесс прост.

После реализации ИИ должен завершить работу с тремя краткими разделами:

1.  **Что я сделал**
2.  **Тестирование**
3.  **Требует вашего внимания**

Итоговый отчет должен быть кратким. Детальные обоснования остаются в файле промпта, а не в длинном сообщении после реализации.

# Раздел 4: Определите правила UI

В этом рабочем процессе ИИ не является дизайнером. Вы должны либо предоставить скриншоты UI, либо интегрировать его с Figma MCP, а ИИ реализует их.

Это должно быть явным, потому что ИИ часто пытается улучшить дизайн. Он может изменить цвета, интервалы, типографику, макет, тени или структуру компонентов, потому что считает, что результат выглядит лучше.

Для этой обучающей платформы правило UI должно быть прямым:

_Ты не занимаешься дизайном UI. Пользователь предоставляет изображения для десктопа и промпт. Воспроизведи эталон точно, включая макет, интервалы, типографику, цвета и состояния._

Затем объясните поведение на мобильных устройствах:

_Нет эталона для мобильных устройств, поэтому сделай страницу адаптивной и разумной, сохраняя при этом точность десктопного эталона._

Это дает ИИ правильный баланс. Десктоп должен соответствовать скриншоту. Мобильная версия должна адаптироваться чисто, поскольку мобильного скриншота нет.

Также укажите ИИ повторно использовать существующие компоненты и паттерны Tailwind перед добавлением новых. Это обеспечивает согласованность приложения на всех страницах и предотвращает внедрение нового визуального стиля в каждой функции.

Самое важное правило:

_Когда есть эталонное изображение, оно является источником истины._

Это предотвращает отношение ИИ к скриншоту как к необязательному предложению.

Этот раздел посвящен снижению неопределенности. ИИ должен использовать реальные инструменты проекта, а не то, что он помнит из старых примеров.

# Раздел 6: Объясните обязанности приложения

Этот раздел указывает ИИ, где находятся обязанности. Он защищает проект от грязного кода и небезопасных сокращений.

Для этой обучающей платформы четко объясните основные обязанности.

- Приложение для учащихся отображает сохраненный контент.
- Sanity Studio предназначена для создания контента.
- Clerk отвечает за аутентификацию.
- PostHog собирает аналитику продукта.
- Поисковый API работает на сервере.
- Браузер отображает UI и вызывает безопасные маршруты приложения.
- Конвейер обработки видео работает как автономный инструмент.

Самая важная граница — между браузером и сервером.

- Браузер не должен хранить приватные токены.
- Он не должен вызывать LLM напрямую.
- Он не должен вызывать Sanity Context MCP напрямую.
- Он не должен записывать контент или прогресс напрямую.

Простое правило:

_Браузер только показывает UI и вызывает безопасные маршруты приложения. Доступ к приватным данным и вызовы ИИ происходят на сервере._

Для этого проекта это защищает токены чтения Sanity, токены записи Sanity, секретные ключи Clerk, приватные ключи PostHog, ключи OpenAI и учетные данные Sanity Context.

Этот раздел предотвращает одни из самых опасных ошибок ИИ. Функция может выглядеть работающей и при этом быть неверной, если она раскрывает секреты или переносит серверную работу в браузер.

# Раздел 8: Зафиксируйте уже принятые решения

Этот раздел предотвращает повторное принятие ИИ тех же продуктовых вопросов во время каждой функции.

Для обучающей платформы решения включают следующее:

1.  Поиск — это полноценная страница результатов, а не чат-бокс.
2.  Результаты поиска — это структурированные карточки.
3.  Поиск основан на данных Sanity.
4.  Интеллектуальные данные о видео хранятся в документах видео.
5.  Временные метки сначала разрешаются по главам, а затем по фрагментам транскрипта.
6.  Воспроизведение остается на сайте через встраиваемые плееры провайдеров.

Решения по данным также важны.

- Модули встроены внутрь курсов.
- Уроки — это отдельные документы.
- Номера уроков выводятся из порядка.
- Прогресс привязан к идентификатору пользователя Clerk.
- PostHog отслеживает значимые события обучения.

Этот раздел важен, потому что ИИ может попытаться проявить креативность. Он может создать чат вместо карточек результатов, создать документ модуля, хранить родительский курс непосредственно в уроках, показывать необработанные видео-документы как результаты или отправлять учащихся на YouTube.

Раздел решений говорит ИИ, что эти выборы уже сделаны. Стройте в соответствии с ними, если пользователь не изменит их.

# Раздел 9: Определите модель данных

Для обучающей платформы модель данных критична. Приложение настолько же хорошо, насколько хороша структура его контента.

Качество поиска зависит от качества контента. Страницы курсов, страницы уроков, сопоставление транскриптов и результаты по временным меткам — все зависит от четкого моделирования данных.

Поэтому `AGENTS.md` должен определять основные документы и записи.

## Курс (Course)

Курс — это основное, что просматривают учащиеся. Он должен включать: заголовок, слаг, краткое описание, обложку, уровень, цену, необязательный популярный флаг, количество студентов, результаты обучения, ссылку на инструктора, ссылку на категорию и упорядоченные модули.

Курс управляет путем обучения. Это означает, что порядок модулей и уроков принадлежит здесь.

## Модуль (Module)

Модуль встроен внутрь курса. Он не должен быть документом верхнего уровня.

Это важно, потому что модуль имеет смысл только в контексте определенного курса. Модуль под названием "Начало работы" или "Продвинутые концепции" сам по себе бесполезен. Он полезен, потому что принадлежит курсу и содержит уроки в определенном порядке.

Модуль должен включать: заголовок, краткое описание и упорядоченные ссылки на уроки.

## Урок (Lesson)

Урок — это отдельный документ, потому что у него есть собственное содержание. Он должен включать: заголовок, слаг, URL видео, миниатюру или постер, продолжительность, флаг бесплатного предпросмотра, количество студентов, заметки в Portable Text, ключевые моменты, необязательный профессиональный совет и ресурсы.

Уроку не нужно хранить свой родительский курс. Когда приложению понадобится родительский курс, он может получить его через ссылки на уроки в курсе.

## Инструктор (Instructor)

Инструктор должен включать: имя, слаг, фото, специализацию и биографию. Инструкторы могут появляться на страницах курсов, страницах уроков и на собственных страницах инструкторов позже.

## Категория (Category)

Категория должна включать: заголовок, слаг и описание. Категории помогают с просмотром, фильтрацией и организацией курсов.

## Документ видео (Video Document)

Документ видео создается конвейером обработки. Он должен включать: идентификатор видео, URL видео, главы с `startSeconds` и метками, а также фрагменты транскрипта с `startSeconds` и текстом.

Не храните весь транскрипт в одном поле, которое возвращается целиком. Это делает поиск шумным, дорогим и более сложным в управлении.

## Документ контекста агента (Agent Context Document)

Документ контекста агента хранит конфигурацию поиска. Он должен включать фильтр области действия контента и инструкции по поиску.

Это позволяет настраивать поведение поиска без изменения кода приложения каждый раз.

## Запись прогресса (Progress Record)

Прогресс относится к состоянию приложения, а не к контенту. Он должен быть привязан к идентификатору пользователя Clerk и хранить завершенные уроки, а также последнюю позицию учащегося в уроке.

Запись прогресса должна выполняться через серверный маршрут. Браузер не должен записывать прогресс напрямую.

# Раздел 10: Объясните обработку видео

У урока есть URL видео, но одного URL видео недостаточно для поиска. Если учащийся спрашивает, где объясняется промежуточное ПО Clerk, приложению нужно знать, что сказано внутри видео.

Вот почему проекту нужна обработка видео.

Обработка видео — это автономный процесс. "Автономный" не означает отключенный от интернета. Это означает, что работа выполняется вне обычного запроса учащегося.

Скрипт читает данные транскрипта и глав, создает полезные фрагменты с временными метками и сохраняет их как видео-документы в Sanity. Позже поиск может использовать эти подготовленные видео-документы.

Приложение не должно извлекать транскрипты, разбивать текст и записывать видео-документы в то время, как учащийся выполняет поиск. Это сделало бы опыт более медленным, дорогим и сложным для отладки.

Правило простое:

_Выполните тяжелую обработку до того, как она понадобится учащимся. Используйте подготовленные результаты, когда учащиеся выполняют поиск._

Также четко определите поддержку провайдеров. Если приложение поддерживает YouTube, Vimeo или Bunny, поддержка означает, что работают как обработка, так и воспроизведение. Не заявляйте, что провайдер поддерживается, если вы можете обработать субтитры, но не можете выполнить перемотку во время воспроизведения, или если вы можете встроить плеер, но не можете создать фрагменты транскрипта.

# Раздел 11: Объясните конфигурацию поиска

Поведение поиска не должно быть скрыто только в коде. Обучающей платформе с AI-поиском нужен способ настройки того, что видит агент и как он себя ведет.

Для этого и нужен документ Context. Он может указать агенту, какие типы контента важны, какие поля приоритетны, какие результаты возвращать и что никогда не раскрывать.

## ФОКУСИРУЙСЯ НА

Для этого проекта поиск должен фокусироваться на контенте, ориентированном на учащихся, таком как: курсы, модули, уроки, заметки к урокам, ключевые моменты, результаты обучения, инструкторы, категории, главы видео и фрагменты транскриптов.

## ИЗБЕГАЙ

Он должен избегать внутреннего или небезопасного контента, такого как: приватные токены, секреты конфигурации, полные массивы транскриптов и необработанные внутренние видео-документы как результаты для учащихся.

Самые важные правила поиска должны жить как в документе Context, так и в системном промпте.

Это может показаться повторяющимся, но это полезно. Если правило критично, повторите его там, где модель, скорее всего, последует ему.

# Раздел 12: Определите, как должен вести себя поиск

Поиск — это особая функция в этой обучающей платформе, поэтому этот раздел должен быть конкретным.

Поиск должен быть полноценной страницей результатов. Он не должен быть крошечным виджетом и не должен быть чат-ботом. Учащийся должен получать ранжированные кликабельные карточки результатов.

Основные типы результатов: результат по моменту видео и результат по уроку.

## РЕЗУЛЬТАТ ПО МОМЕНТУ ВИДЕО

Результат по моменту видео привязан к реальному видеоуроку в определенной секунде. Он должен включать: название курса, метку модуля и урока, миниатюру, краткое описание, совпавшую секунду и действие, которое открывает урок с этой секунды.

## РЕЗУЛЬТАТ ПО УРОКУ

Результат по уроку — это урок, совпавший по теме. Он должен включать: курс, метку модуля и урока, ключевые моменты урока, краткое описание и действие для открытия урока.

- Сам видео-документ не должен показываться как результат. Учащийся должен видеть урок, а не внутренний документ для поиска.

Поиск должен соответствовать как темам уроков, так и моментам видео. Он должен ранжировать конкретные совпадения выше, чем слабые совпадения. Название урока, которое напрямую содержит искомое понятие, должно ранжироваться выше, чем заметка, которая один раз упоминает широкое ключевое слово.

Самое главное, поиск должен быть обоснованным. Он никогда не должен выдумывать курсы, уроки, инструкторов, URL-адреса, цены, продолжительность, временные метки или количество результатов.

Каждый результат должен исходить из реальных данных.

# Раздел 13: Перечислите распространенные ловушки

Этот раздел помогает ИИ избежать ошибок, которые не очевидны из кода.

Для этой обучающей платформы стоит записать несколько ловушек.

- Sanity Context может потребовать развернутого Studio-приложения, прежде чем набор данных сможет обслуживаться.
- Семантический поиск может быть не включен, поэтому может потребоваться резервный вариант по ключевым словам.
- Промпты с шаблонными литералами могут сломаться, если не экранировать обратные кавычки.
- Изменения промпта поиска могут потребовать перезапуска сервера.
- Не следует возвращать целые массивы транскриптов, так как они могут переполнить контекст и создать шумные результаты.
- Набор данных является приватным, поэтому токены чтения должны оставаться на серверной стороне.

Также напомните ИИ, какие значения безопасны для браузера, а какие нет.

**БЕЗОПАСНЫ ДЛЯ КЛИЕНТА:**
Публикуемые ключи Clerk и публичные ключи проектов PostHog безопасны для клиента.

**НЕ БЕЗОПАСНЫ ДЛЯ КЛИЕНТА:**
Секретные ключи Clerk, токены Sanity, ключи OpenAI и приватные ключи PostHog небезопасны.

Этот раздел полезен, потому что ИИ может написать код, который выглядит правильным, но не работает в реальной среде. Практические предупреждения помогают ему избежать известных ошибок.

# Раздел 14: Определите проверки для запуска

ИИ никогда не должен утверждать, что что-то работает, без проверки.

Скажите ему точно, что запускать. Для этой обучающей платформы обычные проверки включают: линтинг, проверку типов, production-сборку (при изменении маршрутов или серверного кода), сервер разработки и ручное тестирование в браузере.

Для работы с Sanity ИИ должен проверить, что Studio открывается, схемы отображаются правильно, контент может быть создан, импорт работает, а настройка Context действительна, когда поиск зависит от него.

Для работы с поиском и обработкой он должен тестировать с реальными запросами учащихся, несвязанными запросами, пустыми состояниями, отсутствием выдуманных результатов, поведением временных меток, а также с реальным набором данных или конечной точкой MCP, когда это необходимо.

Правило должно быть прямым:

_Сообщи о реальных результатах. Никогда не утверждай, что проверка пройдена, не запустив ее._

Это делает ИИ подотчетным.

# Раздел 15: Добавьте раздел "В случае сомнений"

Завершите файл простыми запасными правилами. Это дает ИИ точку сброса, когда задача неясна.

Для этого проекта правила можно записать так:

- Делай это маленьким.
- Используй соответствующий навык.
- Соблюдай границы между сервером и клиентом.
- Держи приватные токены в секрете.
- Точно соответствуй предоставленному UI.
- Проверь настройки и конфигурацию перед жестким кодированием.
- Сохрани промпт и получи утверждение перед написанием кода.
- Запусти проверки.
- Предоставь точные шаги тестирования.

Когда ИИ не уверен, он не должен импровизировать. Он должен вернуться к этим правилам.

# Как написать AGENTS.md для собственного проекта

Самый простой способ написать сильный `AGENTS.md` — строить его от проекта. Не начинайте с общих правил для агентов. Начните с того, чем на самом деле является продукт.

## 1. Опишите продукт простым языком

Напишите один четкий абзац.

Для этой обучающей платформы это может быть так:

_Это обучающая платформа, где авторы создают курсы в Sanity, а учащиеся просматривают курсы в приложении Next.js, открывают уроки, смотрят видео и ищут информацию по учебному контенту. Выдающейся функцией является интеллектуальный поиск, который возвращает обоснованные карточки результатов и может ссылаться непосредственно на точные моменты в видеоуроках._

Если вы не можете четко написать этот абзац, вы не готовы писать полный `AGENTS.md`.

## 2. Перечислите основные пользовательские потоки

Для обучающей платформы основные потоки просты. Учащийся просматривает каталог, открывает курс, открывает урок, смотрит видео, ищет тему, открывает результат поиска, а затем возобновляет или завершает уроки. Автор управляет контентом в Sanity Studio.

Эти потоки говорят ИИ, что на самом деле делает продукт. Они также помогают определить порядок сборки.

## 3. Перечислите инструменты и объясните, зачем нужен каждый

Не просто перечисляйте инструменты. Объясните их задачи.

- Next.js обслуживает приложение для учащихся.
- Sanity хранит контент курсов и уроков.
- Sanity Studio — это интерфейс для авторов.
- Clerk отвечает за аутентификацию.
- PostHog отслеживает поведение продукта.
- Sanity Context MCP подключает AI-поиск к контенту Sanity.
- OpenAI обеспечивает логику поиска.
- Tailwind отвечает за стилизацию.
- Zod проверяет структурированный вывод.

Это предотвращает замену вашего стека или использование неправильного инструмента для функции.

## 4. Определите границы

Здесь проект становится безопасным.

Например, браузер никогда не хранит приватные токены, никогда не вызывает LLM напрямую, никогда не вызывает MCP напрямую и никогда не записывает контент или прогресс напрямую. Чтение контента Sanity происходит на серверной стороне. Запись прогресса происходит через серверные маршруты. Обработка видео выполняется автономно. Поиск возвращает структурированные карточки, а не чат.

Эти правила должны быть четко записаны, потому что они предотвращают опасные сокращения.

## 5. Определите модель данных

Сделайте это до начала кодирования.

Для этой обучающей платформы определите: Курс, Модуль, Урок, Инструктора, Категорию, Видео, Контекст Агента и Прогресс. Объясните, что хранит каждый из них и как они связаны.

Это предотвращает плохие схемы, дублирование связей и запутанный доступ к данным в будущем.

## 6. Определите поведение основных функций

Для важных функций пишите правила напрямую.

**ПОИСК:**
Для поиска укажите, что он должен быть обоснованным, возвращать структурированные карточки, поддерживать результаты по урокам и моментам видео, использовать главы перед фрагментами транскрипта для временных меток, никогда не выдумывать данные и никогда не раскрывать полные фрагменты транскриптов.

**ВИДЕО:**
Для видео укажите, что воспроизведение остается на сайте, использует встраиваемые плееры провайдеров, не использует собственный видеоплеер и использует параметр запроса `startSeconds` для глубоких ссылок.

**АНАЛИТИКА:**
Для аналитики укажите, что PostHog отслеживает значимые события обучения и не должен получать приватные токены или конфиденциальные данные.

## 7. Определите рабочий процесс ИИ

Здесь вы дисциплинируете ИИ.

Скажите ему не кодировать сразу. Он должен прочитать `AGENTS.md`, прочитать соответствующие навыки, изучить существующий код, создать промпт для реализации в папке `prompts`, запросить утверждение, начать разработку только после утверждения, запустить проверки и сообщить с разделами "Что я сделал", "Тестирование" и "Требует вашего внимания".

Это превращает случайные запросы в повторяемый рабочий процесс.

## 8. Определите проверки и ручные тесты

Не оставляйте тестирование расплывчатым.

Укажите ИИ запускать линтинг, сборку, проверку типов (если доступно), открывать приложение в браузере, тестировать счастливый путь, тестировать пустые состояния, тестировать неверные вводы, проверять Studio при изменениях Sanity, проверять PostHog при изменениях аналитики и тестировать поиск с реальными и несвязанными запросами.

Это делает "сделано" измеримым.
